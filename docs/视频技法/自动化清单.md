## 一、已经写成脚本的（`scripts/`，现在就能跑）

| 脚本 | 覆盖清单项 | 干什么 | 依赖 |
|---|---|---|---|
| `vshot_report.py` | A1–A7、C5（字幕带交叉） | 抽 10fps 灰度帧，逐帧算：帧差、主体带高度（景别）、主体水平重心、画面中位亮度；输出静止段、取景变化点、景别动态范围、逐镜头景别序列 | 标准库 + `ffmpeg` |
| `vsubtitle_check.py` | C1–C5 | 用**横向梯度**找字幕行（亮底/暗底通用），输出行数、字号、左右/底部安全区、与主体重叠率，可出带检测框的调试图 | 标准库 + `PIL` + `ffmpeg` |
| `vaudio_check.py` | D1–D4 | `loudnorm` 量整片 I/TP/LRA，`astats` 量削波，分段再量响度曲线 | 标准库 + `ffmpeg` |
| `vtone_check.py` | B1–B2 | **原分辨率**抽帧统计 P0.5/P50/P99.5、暗部面积、饱和度、死白死黑 | 标准库 + `PIL` + `ffmpeg` |
| `vcommon.py` | — | 共用：ffmpeg/ffprobe 定位、规格探测、流式抽帧、直方图分位 | 标准库 |

四个脚本都返回退出码 `0=PASS / 1=FAIL`，可以直接串到发布流水线里：

```bash
set -e
PY=/opt/homebrew/bin/python3.14
for s in "vshot_report.py --profile mv" "vaudio_check.py --profile mv" \
         "vtone_check.py --profile water-ink"; do
  $PY scripts/${s%% *} "$V" ${s#* } || { echo "自检失败: $s"; exit 1; }
done
```

## 三、写不了的（明确不做，别浪费时间）

| 想自动化的事 | 为什么不行 |
|---|---|
| **自动判断"这个镜头好看"** | 构图好坏取决于意图（中心构图在标题卡上是优点，在叙事镜头里是偷懒）。没有可判定的目标函数。 |
| **自动检测"切点是否在正确的情绪位置"** | 可以把切点对齐到拍点（A6），但"这里该不该切"是剪辑判断，不是测量。 |
| **自动判断转场是否生硬** | 能测"叠化时长是否 < 8 帧"（那是数字），测不了"这个叠化是否合适"。 |
| **自动检测"字幕与画面元素的语义冲突"** | 需要理解画面内容。可以用多模态模型做辅助审片，但结论不可复现，不能当判据。 |
| **自动判断"音乐段落与画面段落是否匹配"** | `manifest.json` 有 sections，但"这段音乐该配什么画面"没有客观答案。只能做**一致性检查**（画面事件密度是否随音乐能量单调上升），这可以写，但价值低于 1–8 项。 |
| **自动检测场景切换（cut detection）** | 实测在"纸上一行字慢慢写"这类素材上不可用：ffmpeg `scdet` 在 40s 样片上给出 15 个假切点，全在换行处。所以清单里改成"取景变化点"+ 手工 EDL（`--cuts`）。 |

## 三点五、"镜头类"交付的主证据必须是曲线，不是静帧

**结论：凡是交付/汇报"镜头有没有变、节奏有没有起来"，主证据放 zoom–时间曲线，
静帧只当辅助。**（2026-11-02 由 `compare_v1_v3.jpg` 验证）

```
1. zoom(t) 曲线（v1 一条平线 + 18.7s 长平台；v3 每乐句在 0.5↔1.25 锯齿）
   ← 这一张就把"镜头终于会动了"说完了
2. 时间条带：同一区段取 6 个时刻，上行旧版 / 下行新版
   ← 补"具体长什么样"
3. 单点静帧对照：最弱，两个版本在"停住"相位长得几乎一样，会让人误判"没变化"
```

为什么：静帧只能表现**取景**，表现不了**运镜**。而"一个镜头里一个字变来变去"
说的是运镜的有无，不是某一帧的构图。我第一次做的 4 组静帧对照就吃了这个亏——
两边看起来几乎一样，差点得出"没改动"的错误结论。

曲线怎么画：`vcamera_report.py --keys x.json` 已经把 `cameraAt(t)` 复刻成 Python 了，
直接 `[camera_at(keys, t)[2] for t in ts]` 就能取到 zoom 序列，PIL 画折线即可。
**别用 ffmpeg 抽帧去反推相机**——那条路我们验过，测不准（见 §三）。

## 四、脚本的实现约定（以后再写新脚本请保持一致）

1. **流式抽帧**：`ffmpeg ... -f rawvideo -` 走 `stdin`，不落临时文件。4K 也不吃内存。
2. **分析分辨率**：长边 320 够量帧差/景别；**要量影调、浓度这类"一两个像素"的量，
   必须原分辨率**。这条 2026-11-02 又踩了一次：
   `check_overflow` 的越界浓度在 960 宽抽帧上量到中位 alpha **0.349（假通过）**，
   同一批帧回原分辨率 1920 是 **0.357（不通过）**——2×2 下采样把边缘那一两个像素吃掉了。
   **凡是判据阈值在 0.05 量级的，一律原分辨率。**
   缩到 320 会把细笔画的墨芯和纸平均掉（实测同一帧满幅 min=13，缩到 320 后 P0.5=102，
   得出"暗部面积 0.0%" 的假结论）。
3. **阈值要自适应**：绝对阈值在不同内容上必翻车。字幕检测用
   `max(6, 2.5 × 该区行梯度中位数)` 加带级峰值门槛，才同时吃得下"纸面底噪 2"和"裙子底噪 15"。
4. **输出必须带判据**：`[PASS/FAIL] 指标 实测值 判据`，不给"看起来还行"。
5. **退出码**：`0` 全过，`1` 有失败。方便 `set -e` 串流水线。
6. **调试图**：凡是要人眼确认的（字幕框、重心轨迹），必须能一行参数输出 PNG。

## 五、这轮的三个方法论教训（2026-11-02 · 《红昭愿》镜头改版）

> 都是踩出来的，写下来免得下次重踩。三条都是关于**"怎么证明改好了"**，不是关于代码。

### ① 静帧证明不了"会动"，镜头类交付的主证据必须是曲线

**踩法**：改完镜头后做了 4 组同时间点静帧对照（左改前 / 右改后），两边看起来几乎一样，
差点得出"没改动"的错误结论。

**为什么错**：静帧只能表达**取景**，表达不了**运镜**。而"一个镜头里一个字变来变去"
投诉的是**运镜的有无**。两个版本在"停住"相位必然长得相似——那只说明"停在那儿的构图一样"，
不说明"它会不会动"。

**正确做法**：主证据放 **zoom–时间曲线**，静帧只当辅助。

| 优先 | 证据 | 作用 |
|---|---|---|
| 1 | zoom(t) 曲线 | 一眼看出"旧版一条平线 + 18.7s 长平台" vs "新版每乐句在 0.5↔1.25 锯齿" |
| 2 | 同一区段 6 个时刻的时间条带 | 补"具体长什么样" |
| 3 | 单点静帧对照 | 最弱，只用于证明局部改善（字幕位置、纸纹接缝、墨色） |

曲线怎么画：`vcamera_report.py` 已经把 `cameraAt(t)` 复刻成 Python 的 `camera_at()`，
直接取 `[camera_at(keys, t)[2] for t in ts]`，PIL 画折线即可。
**不要用 ffmpeg 抽帧反推相机**——那条路验过，测不准（见 §三）。

### ② 凡 0.05 量级的量（浓度 / 影调）一律原分辨率

**踩法**：给 `check_overflow.py` 加"越界列浓度"时，直接在既有的 **960×540** 抽帧上量，
得到中位 alpha **0.349**，刚好"通过" <0.35 的判据。回原分辨率 1920 一量是 **0.357**，不通过。

**原因**：960 宽是从 1920 按 2×2 平均下来的，而越界区域往往只有 **5–11 列**、
每条墨只有一两个像素宽。2×2 平均把那一两个像素和周围的纸混在一起，淡影被吃掉。

**规则**：
- 判据阈值在 **0.05 量级**（alpha、黑位、饱和度、颗粒幅度）→ **必须原分辨率**；
- 几何量（包围盒、越界列数、字幕 bbox）可以在缩略图上量，误差远小于阈值；
- 脚本里如果为了速度先缩图，**对判定的那几帧要回原分辨率复算一遍**
  （`check_overflow.py` 现在就是对越界帧做这个回算，并且顺带纠正了
  "15.0s 那帧在原分辨率下其实没越界"这个假阳性）。

### ③ 改前 / 改后两侧必须同源或现渲，不许拿来源不明的历史文件当基线

**踩法**：拿 `mv_art_full.mp4`（mtime 12:10）当"改前"，抽 70/90/125/140s 做对比图发了出去。
后来发现 `mv-art.html` 的最后修改是 **14:16** —— 那个整片是**更早版本**渲的，根本不是长卷 v1。
逐帧核对，四帧全部对不上（70s：61% vs 18%；125s：56% vs 13%）。

**规则**：
- 对比图的"改前"要么**从版本备份的页面现渲**（`mv-art.html.bak` + `src/_v1ink.js`），
  要么**来自同一次构建**；
- 拿历史文件之前先核 **mtime 与源文件 mtime 的先后**，晚于源码的文件才有可能是它渲的；
- 更稳的做法是根本不依赖历史文件：**基线用代码路径**（`cameraAt` 的 keys），
  现渲只需几秒，且与"当初真渲出来会长什么样"严格等价。
